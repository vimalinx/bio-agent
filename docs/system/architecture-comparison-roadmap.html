Architecture Comparison and Roadmap

这里的结论不是“抄谁”，而是明确 `bio-agent` 当前应该收敛成什么产品：control-plane-first hybrid。

最准确的判断是：`bio-agent` 强在 plan/session/benchmark 真相层，ClawBio 强在 packaged reproducible delivery，LabClaw 强在 breadth / catalog coverage。正确路线是保留你自己的控制平面，再补 hero runner、repro bundle、capability catalog 与稳定验证面。

因此当前不应该做 wet-lab / XR / robotics pivot，也不应该做第二套 orchestrator。

目标架构

bio-agent target architecture

user request
  -> control plane (canonical truth)
     -> request normalization
     -> candidate plans
     -> approval + session state
     -> run.json / run-status.json / run-review.json
     -> analysis flow contract
     -> benchmark fit / scorecard
  -> hero runner surface (thin adapter only)
     -> normalized product-facing inputs
     -> stable output directory shortcuts
     -> automatic reproducibility bundle
  -> capability plane
     -> evidence-derived capability catalog
     -> execution tier / runtime mode / verification level
     -> first_party_executable / bridge_executable / reference_only

重点不是“再造一个更简单的执行器”，而是让 hero runner 明确依附在现有 session/run 真相层之上。

必须保留 `run.json`、`run-status.json`、`run-review.json` 作为执行真相；product-facing 命令只能是薄适配层。
必须新增 automatic reproducibility bundle、capability maturity labeling、stable CI / smoke proof。

Hero Lanes

Lane 1 — RNA-seq differential expression 从已有 grounded family 直接产品化，目标是把 session path 包装成更短的 runner，同时继续落回 canonical session/run artifacts。
Lane 2 — Germline short variant discovery 沿用 benchmarked family，补 demoability、repro bundle、smoke coverage，并保持 truthful blocked state 输出。
Lane A — Hero runner surface 输入更产品化，但底层仍复用现有 session lifecycle；绝不变成 second orchestrator。
Lane B — Reproducibility bundle hero runs 默认输出 `commands.sh`、environment snapshot、`checksums.sha256`、`provenance.json`、`delivery-bundle.json`。
Lane C — Capability catalog 从 evidence-bearing metadata 生成 catalog，显式标记 `first_party_executable` / `bridge_executable` / `reference_only`。

硬约束

no second orchestrator canonical run truth only no wet-lab / XR pivot hero workflows over raw skill count phase-2 crystallization gate
Capability honesty catalog 必须区分 `first_party_executable`、`bridge_executable`、`reference_only`；不能再让定义数量自动等价于可执行承诺。
Crystallization gating session-to-skill crystallization 不是 phase 1 的前置条件；要等 hero lanes、repro bundle、stable review/status artifacts、smoke/CI 证明成立后再进入 phase 2。

阶段路线

Phase 1: Product surface proof 做薄 hero runner、自动 reproducibility bundle、comparison/docs packaging，让两条 hero lane 先能稳定演示。
Phase 2: Capability + crystallization gate 在 phase 1 证据成立后，再引入 evidence-derived capability catalog 与受控的 session-to-skill crystallization loop。
Phase 3: Broader connectors 只有在 truth model、packaging、CI 稳定后，才考虑扩更多 bridge / connector surfaces；不是先追 skill count，更不是先转向 wet-lab / XR。
默认验证面 stable control-plane regression lane + hero-runner smoke lane + optional heavy integration lane。
路线句子 `bio-agent` 不是要变成 ClawBio 或 LabClaw，而是要把 control plane 变成可信产品骨架，再把 delivery / catalog / docs 补齐。
